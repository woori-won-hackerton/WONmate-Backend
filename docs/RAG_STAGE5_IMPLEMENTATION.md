# 5단계: 보험약관 RAG 질의응답

> 현재 API 계약은 [6단계 구현 문서](RAG_STAGE6_IMPLEMENTATION.md)와 [API 사용 예시](RAG_API_EXAMPLES.md)를 따른다. 이 문서는 5단계 당시의 구현 기록이며, 자동 유형 판단·productIds 입력·비교/추천 미지원 설명은 현재 동작과 다르다.


`POST /api/rag/ask`는 질문에 관련된 보험약관·상품요약서를 검색하고 GPT 답변과 검증된 출처를 반환한다. 질문·답변을 DB에 저장하지 않으며 대화 이력 테이블을 생성하지 않는다. 상품 비교·추천은 구현하지 않는다.

## 요청

### 요청 형식 변경사항

| 항목 | 변경 전 | 현재 |
| --- | --- | --- |
| 질문 분류 | `questionType` 필수 | 필드 제거, 질문과 원문을 바탕으로 GPT가 필요한 설명 판단 |
| 상품 범위 | `productIds` 하나 필수 | 선택, 생략/null/빈 배열은 전체 상품 검색 |
| 검색 문서 유형 | 질문 분류에 따라 결정 | 약관과 상품요약서에서 검색 |
| 제한 조항 검색 | 지정 상품의 약관 검색 | 기본 검색에 나온 상품별로 약관 검색 |
| 추가 검색 수 | 지정 상품에 topK 적용 | 상품별로 배분하며 전체 합계 topK 유지 |

기존 클라이언트는 요청에서 `questionType`을 제거한다. 상품을 선택한 경우에만 `productIds`를 보낸다. 응답의 `answer`와 `sources` 구조는 유지된다.

질문 분류 입력은 제거했다. 질문만으로 요청할 수 있다.

```json
{
  "question": "암 관련 보장 내용 찾아줘",
  "topK": 5
}
```

특정 상품만 검색하려면 선택 필터를 지정한다.

```json
{
  "question": "암 진단비 지급 조건은?",
  "productIds": [6],
  "topK": 5
}
```

- `question`: 필수, 공백 불가, 최대 2,000자.
- `productIds`: 선택, 생략/null/빈 배열이면 전체 상품에서 검색한다. 지정할 때는 양수 상품 ID 하나를 받는다.
- `topK`: 선택, 기본 5, 범위 1~20. 기본 검색에서 최대 topK개, 상품별 제한 조항 추가 검색에서 합계 최대 topK개를 가져온다. 중복 제거 후 최대 2×topK개가 GPT에 전달된다. 1이면 검색 범위가 좁아 보장 내용을 충분히 찾지 못할 수 있다.

Swagger 요청 예시도 상품 ID와 질문 분류 없이 호출하는 형태로 변경했다. 서버 재시작 후 Swagger 페이지를 새로고침하면 반영된다.

## 처리 및 출처

1. 입력을 검증하고 선택된 상품 필터로 TERMS/SUMMARY를 검색한다.
2. 검색된 상품별로 원래 질문에 면책·감액·보장개시일·지급 제한 검색어를 붙여 TERMS를 추가 검색한다. 전체 추가 검색 예산을 검색된 상품에 나누어 적용한다.
3. 질문과 원문을 GPT에 전달한다. GPT는 질문에 필요한 보장 설명·지급 조건·면책·질병 정의를 판단한다. 분류를 위한 별도 GPT 호출은 없다.
4. 상품 미지정 시에는 검색된 상품의 사례로 설명하도록 하고, 상품명(문서명)과 productId를 구분해서 답변하도록 지시한다. 전체 상품에 공통된 조건이라고 일반화하지 않는다.
5. GPT가 선택한 chunkId를 실제 전달된 청크와 대조한다. 문서 메타데이터는 서버가 검색 결과에서 구성한다.

응답은 `answer`, `sources`이며 출처에는 `productId`, `documentId`, `documentName`, `documentType`, `chunkId`, `sectionTitle`, `startPage`, `endPage`가 포함된다. 미검색 출처나 지정 상품 밖의 청크는 오류 처리한다. 검색 결과가 없으면 GPT를 호출하지 않으며, 출처가 없는 답변은 확인 불가 안내로 반환한다. 응답 중단·거절·잘못된 JSON도 정상 답변으로 반환하지 않는다.

`OPENAI_API_KEY`, `OPENAI_CHAT_MODEL`을 사용한다. 모델 기본값은 `gpt-6-luna`다. Chat Completions strict JSON schema와 `store:false`를 사용한다. [공식 구조화 응답 규격](https://developers.openai.com/api/docs/guides/structured-outputs)을 따른다. GPT 호출 중 DB 트랜잭션을 유지하지 않고 운영 클라이언트는 질문·답변 본문을 로깅하지 않는다.

## 상품 ID와 문서 ID

현재 로컬 상품 ID는 6~15, 문서 ID는 9~28이다. `product_01` 디렉터리는 상품 ID 1을 의미하지 않는다. 상품 ID는 상품을, 문서 ID는 개별 PDF를 식별하며 하나의 상품에 약관과 상품요약서 등 여러 문서가 연결된다. `GET /api/documents`에서 실제 매핑을 확인한다.

ID는 `GenerationType.IDENTITY`로 자동 생성한다. PostgreSQL 자동 증가 시퀀스는 삽입이 롤백되거나 데이터가 삭제되어도 소비한 번호를 재사용하지 않는다. 이 프로젝트의 DB 통합 테스트도 상품과 문서를 생성하고 롤백하므로 번호가 건너뛸 수 있다. 최초 번호가 소비된 정확한 실행 이력은 별도로 기록되어 있지 않다. ID는 연속 순번이나 상품 개수를 의미하지 않는다. 기존 ID와 외래 키 참조는 재번호 부여하지 않았다.

## 검증

기존 구현에서는 상품 6의 보장 설명·지급 조건·면책/감액·암 정의·약관에 없는 질문을 실제 GPT 호출로 검증했고 출처 메타데이터를 DB와 대조했다. HTTP에서도 상품 1은 검색 근거가 없고 상품 6은 답변과 출처를 반환하는 것을 확인했다.

이번 변경에서는 상품 필터 생략/null/빈 배열 허용, 잘못된 입력 거부, 전체 상품 검색 후 상품별 제한 조항 검색, 추가 검색 예산, 지정 상품 혼입 차단, 미검색 출처 차단을 자동 테스트로 검증했다. 변경 후 상품 미지정 실제 GPT 호출은 자동 승인 검토가 외부 전송 범위 확대를 이유로 거부하여 실행하지 못했다. 해당 검증은 완료로 간주하지 않는다.

```powershell
.\gradlew.bat test
# 실제 DB 및 유료 GPT 요청: 외부 전송이 승인된 환경에서 명시적으로 실행
$env:RAG_ASK_LIVE='true'
.\gradlew.bat test --tests '*RealAskTests' --rerun-tasks
```

실제 테스트의 출력은 Gradle 로컬 보고서에 남으며 DB 대화 이력은 저장하지 않는다.

## 한계

전체 상품 검색은 관련도가 높은 일부 원문을 찾는 기능이며 모든 상품을 빠짐없이 조사하는 기능이 아니다. 제한 조항 추가 검색도 전체 약관의 모든 면책·감액 조건을 보장하지 않는다. 출처 존재 검증은 답변의 모든 문장이 해당 조항으로 뒷받침됨을 보장하지 않으므로 실제 상담에서는 반환된 페이지와 해당 보장의 전체 조항을 확인해야 한다.
