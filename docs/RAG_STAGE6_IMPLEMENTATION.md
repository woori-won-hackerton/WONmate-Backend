# 6단계: 질문 유형을 선택하는 통합 보험 상담 API

`POST /api/rag/ask` 하나로 용어 설명, 보험 개념 설명, 상품 설명, 상품 비교, 상품 추천을 처리한다. 프론트에서 질문 유형을 먼저 선택하고 **상품 설명일 때만 특정 상품 하나를 선택**한다. 기존 answer/sources 응답과 질문 이력 비저장 정책은 유지한다.

상세 요청·응답과 호출 예시는 [통합 RAG API 사용 예시](RAG_API_EXAMPLES.md)를 참고한다.

## 프론트 요청 계약

| 프론트 표시 | questionType | productId |
| --- | --- | --- |
| 용어 설명 | TERM_EXPLANATION | 생략/null |
| 보험 개념 설명 | INSURANCE_CONCEPT | 생략/null |
| 상품 설명 | PRODUCT_EXPLANATION | 양수 ID 하나 필수 |
| 상품 비교 | PRODUCT_COMPARISON | 생략/null |
| 상품 추천 | PRODUCT_RECOMMENDATION | 생략/null |

- question: 필수, 공백 불가, 최대 2000자.
- questionType: 필수, 위 enum 중 하나. 질문 자동 분류를 대신한다.
- productId: 상품 설명에만 허용하는 단일 양수 ID. GET /api/documents의 상품 ID를 이용한다.
- topK: 선택, 기본 5, 범위 1~20. 검색별 청크 수다.
- 기존 productIds 배열은 요청 계약에서 제거했다. 프론트는 질문 유형 변경 시 선택한 productId를 비우고 상품 설명일 때만 전송한다.
- 유형 누락/잘못된 enum, 상품 설명의 ID 누락, 다른 유형의 ID 전송, 0 이하 ID, 배열 형태 productId는 400이다.

```json
{"questionType":"TERM_EXPLANATION","question":"면책기간과 감액기간이 무슨 뜻이야?"}
```

```json
{"questionType":"INSURANCE_CONCEPT","question":"갱신형 보험과 비갱신형 보험의 차이를 설명해줘"}
```

```json
{"questionType":"PRODUCT_EXPLANATION","productId":6,"question":"입원 관련 보장을 요약해줘"}
```

```json
{"questionType":"PRODUCT_COMPARISON","question":"자녀가 7살이고 입원비가 걱정되는 고객에게 어린이 보험의 보장과 면책 조건을 비교해줘"}
```

```json
{"questionType":"PRODUCT_RECOMMENDATION","question":"52세 고객이고 월 예산은 50000원 정도야. 암 진단비를 우선하는 보험 추천해줘"}
```

## 처리 방식

상품 설명은 선택된 상품의 SUMMARY, 질문 관련 TERMS, 면책·감액·보장개시일·지급제한 TERMS를 독립 검색한다. 다른 상품의 청크 유입을 거부한다.

비교 질문에 카탈로그의 상품명(공백·무배당·우리WON하는 접두사 생략 포함)이 명시되면 해당 상품들을 독립 검색한다. 명시된 상품은 요약서가 없더라도 약관 검색을 수행한다. 그 외 유형과 대상이 명시되지 않은 비교는 insurance_products 목록을 조회하고 상품별 SUMMARY를 독립 검색한다. 요약서 유사도가 높은 최대 5개 후보에 대해 TERMS 및 제한 조건을 상품별로 검색한다. 복잡한 추천 알고리즘이나 가입 심사는 수행하지 않는다. 중복 제거 전 상품별 최대 3×topK 청크를 제공한다.

서버는 선택한 questionType과 검색 근거의 정식 상품명을 GPT에 전달한다. 상품 설명용 productId는 백엔드 검색 범위 지정에만 사용하며 LLM 입력 메타데이터에서는 제외한다. 용어·개념은 문서 근거로 설명하고 특정 약관의 조건을 모든 보험의 공통 정의로 일반화하지 않는다. 문서에 없는 개념은 확인 불가로 안내하며 일반 지식만으로 생성하지 않는다.

비교는 질문의 관심 보장과 검색된 후보를 바탕으로 공통점·차이점·지급조건·면책을 정리한다. 질문에 특정 상품명이 있으면 해당 근거가 제공되었는지 확인하도록 지시한다. 근거가 있는 상품이 2개 미만이면 비교 불가를 명시한다. 상품명만으로 대상을 정확히 식별하거나 모든 상품을 빠짐없이 비교하는 것은 보장하지 않는다.

추천은 관심 보장과 우선순위에 맞는 후보별 이유·주의사항과 FC 검토용 후보라는 안내를 제공한다. 구조화된 고객별 보험료·가입 연령 자료를 전달하지 않으며 나이·예산만으로 가입 가능, 예산 충족, 보험료나 최저가를 단정하지 않는다. 동일 가입금액 근거 없는 진단비 우열도 단정하지 않는다.

LLM은 요청 내 근거 순번(evidenceIndex)만 선택하며 백엔드가 범위를 검증하고 해당 검색 결과에서 sources의 모든 기존 필드를 구성한다. sources는 답변 생성에 제공된 근거 중 답변 관련 항목으로 선택된 검색 근거이며, 실제 문장별 인용 관계를 보장하지 않는다. 선택되지 않은 청크는 반환하지 않는다. 검색에 면책이 없다고 면책이 없는 상품으로 단정하지 않는다. 검색 결과가 없으면 GPT를 호출하지 않으며 출처 없는 생성 답변은 근거 부족 안내로 대체한다.

## 개인정보와 대화 상태

customers/consultations는 조회·수정하지 않는다. 질문·응답·이력을 저장하지 않는다. 현재 요청만 처리하며 이전 메시지를 해석하는 대화 메모리는 없다. 후속 요청에도 필요한 질문 유형, 상품 설명용 ID, 선호정보를 포함해야 한다.

일반적인 이름 표기, 휴대폰, 이메일, 주민번호를 임베딩/GPT 호출 전에 마스킹한다. 자유 서술의 모든 개인정보를 검출하는 완전한 익명화는 아니므로 불필요한 개인정보를 입력하지 않는 것이 전제다.

## 검증 및 한계

AskControllerTests는 5개 유형의 정상 요청과 상품 설명 전용 단일 ID 규칙, 잘못된 유형/ID/입력을 검증한다. AskTests는 상품별 독립 검색·면책 추가 검색·카탈로그 비교/추천 탐색·식별정보 마스킹·출처 검증을 확인한다. ChatClientTests는 선택 유형·정식 상품명·근거 순번과 store:false를 검증한다. 또한 LLM 입력 메타데이터에 DB 식별자·PDF 파일명·페이지가 없음을 확인하고 잘못된 순번을 거부한다. AskTests는 선택된 근거만 서버 메타데이터로 반환하는지, 내부 식별자 표현 위반을 본문 변형 없이 원문을 담지 않는 WARN으로 기록하는지도 확인한다.

실제 GPT의 답변 의미와 추천 적합성은 모의 테스트로 보장하지 않는다. 제한 조항 검색도 약관 전체 검토를 보장하지 않는다. 요약서가 없는 상품은 자동 후보 탐색에서 제외되며 상품 설명은 약관을 직접 검색할 수 있다.

5단계 문서의 요청 형식과 자동 유형 판단 설명, 초기 6단계의 productIds 배열 형식은 이 문서로 대체한다.
## 답변 본문과 출처의 책임 분리

기존에는 LLM이 chunkIds를 반환하고 백엔드가 실제 검색 결과와 대조한 뒤 메타데이터를 구성했다. 메타데이터를 백엔드가 구성하는 점은 유지하되, 이제 모델은 실제 DB 식별자를 반환하지 않는다. LLM에는 정식 상품명(insurance_products.product_name), 문서 유형, 원문, 요청 내 1부터 시작하는 evidenceIndex만 제공한다. 원문 자체에 들어 있는 파일명이나 식별자는 자동 삭제하지 않으며 시스템 지침으로 본문 노출을 금지한다.

LLM의 내부 출력은 answer/evidenceIndexes이고 공개 API는 기존 answer/sources 그대로다. 백엔드는 선택 순번의 범위를 검증하고 중복을 제거해 원래 SearchResult로 변환한다. 선택 순번은 실제 인용을 증명하지 않으며 출처를 '검증된 실제 인용 문서'라고 표현하지 않는다. 모델 선택의 의미적 적절성은 별도 검토가 필요하다.

시스템 프롬프트는 본문·비교표에 정식 상품명만 쓰고 내부 식별자, PDF 파일명·경로·확장자, 참고 문서 목록을 표시하지 않도록 한다. 기존 면책·가입 조건·보험료 추측 금지 및 근거 기반 원칙은 유지한다. 정식 상품명이 조회되지 않으면 추측하지 않도록 안내한다.

AskService는 answer에서 productId/documentId/chunkId 및 밑줄·공백 변형 표현을 대소문자 구분 없이 검사한다. 발견 시 유형과 위반 사실만 WARN으로 남긴다. 원문이나 ID 값은 로그에 담지 않으며 답변을 삭제·재작성하거나 재시도하지 않는다. 따라서 위반 답변을 자동 차단하는 기능은 아니다.

## 프론트엔드 출처 표시: 구현 대기

현재 저장소와 인접 디렉터리에 프론트엔드 소스, package.json, 기존 챗봇 UI가 없어 UI 변경 및 프론트 빌드는 수행하지 않았다. 기존 스타일을 유지하려면 실제 프론트 저장소에서 아래 처리가 필요하다.

1. sources를 documentId로 그룹화한다. 같은 문서명이어도 documentId가 다르면 별도 항목으로 유지한다.
2. 각 그룹의 유효한 startPage~endPage 구간을 모아 중복을 제거하고 오름차순으로 정렬한다. 겹치거나 연속된 구간을 병합하면 4~8, 11처럼 표시할 수 있다. 페이지가 없으면 '페이지 확인 불가'로 표시하고 임의의 페이지를 만들지 않는다.
3. 문서명은 그룹당 한 번만 표시한다. productId로 확보한 정식 상품명과 documentType을 이용해 '정식 상품명 상품요약서/약관'으로 표시하는 방법을 우선한다. 메타데이터가 없으면 파일명의 확장자·날짜·밑줄 등 관리 표기를 정리하되 추측한 정식 상품명을 생성하지 않는다.
4. chunkId 등 식별자는 화면에 표시하지 않는다. PDF 원본 파일명과 청크 메타데이터는 API에 그대로 유지한다.
5. 참고 문서는 실제 인용을 보장하는 목록이 아니라 '답변 생성에 제공된 검색 근거'임을 보조 안내로 명시한다.

검증: `gradlew.bat test bootJar` 성공. 실제 외부 GPT 호출 및 프론트 UI 검증은 수행하지 않았다.
## 검색 품질 점검과 추천 답변 개선

### 확인한 기존 흐름

AskService가 원래 질문으로 상품별 SUMMARY를 topK개 조회하고 최고 코사인 유사도로 최대 5개 후보를 선택했다. 후보별 TERMS를 원래 질문과 공통 면책 검색어가 붙은 질문으로 각각 topK개 검색했다. ChunkSearchRepository는 상품·문서 유형·적재 상태·임베딩 모델 조건을 먼저 적용한 다음 pgvector의 정확한 코사인 거리순으로 정렬한다. ANN 인덱스의 후보 누락을 피하는 MATERIALIZED CTE를 사용하며, 최소 관련성 임계값이나 reranking은 없다. topK는 검색당 최대 개수로, 충분히 관련된 문서만 있다는 보장은 아니다.

LLM은 전달된 검색 근거의 순번을 선택하고 백엔드는 실제 검색 결과의 메타데이터로 sources를 구성한다. 따라서 sources에 나타났다는 사실로 LLM이 해당 조항을 실제 문장에 사용했다고 증명할 수 없다.

### 실제 원문으로 구분한 원인

로컬 PostgreSQL에서 chunk 6309(product 11/document 19), 7258(product 12/document 21)를 읽었다. 양쪽 모두 TERMS, PDF 51~52쪽이다. 원문 앞에는 제45조 예금보험 조항이 있지만 뒤에는 `(별표1) 보험금 지급기준표`, `[기준: 보험가입금액 1,000만원]`, 암진단비·계약 경과 기간별 지급 예시가 존재한다. 제목만 보고 무관한 청크라고 판단할 수 없다.

ArticleChunker는 조·주계약·특약 제목에서만 구간을 나누고 별표를 인식하지 않았다. 이에 따라 지급기준표가 앞 예금보험 조항에 합쳐지고 이전 특약 경로도 상속되었다. 확인된 핵심 문제는 청크 경계 및 메타데이터의 대표성 문제다. 추천 질문의 나이·예산 등과 보장 요구가 모두 검색 쿼리에 들어가는 구조 및 상품명과 무관한 후보 순위 선택도 개선 여지가 있었지만, 당시 질의 벡터와 검색 점수가 없어 두 청크의 과거 순위 원인까지 재현했다고 주장하지 않는다. 실제 답변의 사용 조항도 추정하지 않는다.

### 수정 방식과 유지한 범위

- ArticleChunker: 일반적인 별표·별첨 제목에서 앞 조항을 종료한다. 다음 제목 줄을 결합하고 확인되지 않은 앞 특약 경로를 상속하지 않는다. 예금보험 본문과 지급기준표 모두 보존한다. 본문 참조와 점선 목차는 새 경계로 취급하지 않는다.
- RetrievalQuery: 질문에 명시된 진단비·진단금을 검색 앞부분에서 강조하고 SUMMARY에는 주요 보장·지급기준, TERMS에는 지급기준표·지급사유·보험가입금액, 제한 검색에는 면책·감액·보장개시일·지급 횟수를 보강한다. 원래 질문도 보존해 다른 관심 보장이나 비교 기준이 사라지지 않게 한다. 진단비가 명시되지 않은 일반 질문은 기존 검색 쿼리를 유지한다. 이 규칙은 자연어 전체를 이해하는 분류기가 아니다.
- AskService: 비교에 명시된 상품을 카탈로그와 대조하고 각 상품의 SUMMARY/TERMS/제한 조건을 독립 검색한다. 비슷한 이름을 하나로 합치지 않는다. 명시 대상은 요약서 유사도 순위나 요약서 부재 때문에 약관 검색에서 탈락하지 않는다. 오탈자·임의의 별칭을 완전히 해석하는 상품명 인식 기능은 아니다.
- ChatClient: 양쪽 상품에서 독립적으로 확인된 조건만 동일하다고 표현하고 일부 조건 일치를 전체 보장 동일로 확대하지 않는다. 추천은 고객 요구, 후보 선정 이유, 조건별 충족 확인/미충족 확인/확인 필요, 추가 확인 사항을 연결한다. 고객 조건이 있는 추천에만 권장 형식을 적용한다. 적합한 보장 근거가 없는 후보는 추천하지 않으며 확인된 후보를 소수만 제시한다. 예시 금액은 기준 가입금액과 적용 조건을 명시하고 고객 확정 지급액으로 표현하지 않는다.

제목에 따른 제외 목록, 임의 유사도 임계값, 외부 reranker는 추가하지 않았다. 기존 청크들이 실제로 지급기준을 포함하므로 제목으로 제거하면 근거를 잃기 때문이다. DB 스키마·벡터 거리 계산·topK·공개 API 구조·출처 구성 방식은 유지한다. 검색당 청크 수와 자동 후보 수를 늘리지 않았고 새로운 외부 호출도 추가하지 않았다. 프론트 파일은 변경하지 않았다.

### 검증과 전후 차이

`RAG_QUALITY_REVIEW=true`로 ChunkQualityReviewTests를 실행했다. 이 테스트는 DB 읽기와 PDF 읽기만 수행하며 유료 임베딩·LLM 호출, 문서 재적재를 하지 않는다. 실제 PDF의 51~52쪽을 다시 추출해 두 상품 모두 지급기준표가 `(별표1) 보험금 지급기준표`, 시작 페이지 52인 별도 청크로 분리되는 것을 확인했다. 암진단비와 기준 가입금액은 보존되고 표 경로에서 예금보험·이전 중입자 특약이 제거된다. 예금보험 본문도 별도 구간으로 남는다.

로컬 재현 자료는 `build/rag-quality/reported-chunks.json`과 `build/rag-quality/chunk-boundary-comparison.json`이다. 질문·응답 이력을 DB에 저장하는 기능은 추가하지 않았다.

`gradlew.bat test bootJar` 성공: 총 41개, 통과 31개, 건너뜀 10개, 실패/오류 0개. 테스트에는 다음을 포함한다.

- 52세·월 5만원·암 진단비 추천 검색어에 지급·제한 조건 보강 및 복합 관심 보장 보존.
- 실속하나로암보험/실속플러스하나로암보험 비교에서 두 상품 각각 검색, 요약서가 없을 때 약관 검색 유지, 관련 없는 상품 제외.
- 암보장개시일 일반 질문의 검색어 유지.
- 제목이 예금보험이어도 실제 본문에 진단비 지급표가 있으면 일괄 제외하지 않음.
- 실제 PDF 및 합성 입력의 별표 분리, 목차·본문 참조 오분할 방지, 기존 출처 순번 검증.

세 질문에 대한 실제 GPT 답변의 수정 전후 비교 및 검색 정밀도 수치 평가는 수행하지 않았다. 모의 테스트와 PDF 검증 결과를 실제 LLM 추천 품질 향상 수치로 해석하면 안 된다.

### 기존 적재 데이터에 대한 적용 한계

프롬프트·검색 쿼리·상품명 대상 선정은 실행 코드에 즉시 적용된다. ArticleChunker의 새 경계는 새로 청킹하는 문서부터 적용되며 현재 DB의 기존 청크는 수정하지 않았다. 따라서 기존 DB를 그대로 사용하면 sources의 기존 제45조 제목이 계속 나올 수 있고, 본문에 진단비 지급표가 있으므로 그 사실만으로 검색 실패라고 볼 수 없다.

기존 적재 서비스는 파일 해시와 임베딩 모델이 같은 완료 문서를 SKIPPED 처리하므로 단순 ragIngest 재실행만으로 새 경계를 반영하지 않는다. 기존 데이터의 경계까지 반영하려면 대상 문서의 재처리 방법을 정해 청킹·재임베딩·문서 단위 교체를 수행해야 한다. 이번 작업에서는 재임베딩 비용과 기존 청크 ID 교체를 수반하는 재적재를 실행하지 않았다. 표의 셀 관계와 전체 특약 범위 해석도 여전히 원문 검토가 필요하다.

## 검증 실행 방법

```powershell
# 기본 회귀 테스트와 실행 JAR 빌드
.\gradlew.bat test bootJar

# 현재 로컬 DB의 보고된 두 청크 및 원본 PDF 재검증
# 유료 API 호출 없이 읽기만 수행; 해당 ID와 PDF가 없는 환경에는 적용하지 않음
$env:RAG_QUALITY_REVIEW = 'true'
try {
    .\gradlew.bat test --tests '*ChunkQualityReviewTests' --rerun-tasks
} finally {
    Remove-Item Env:RAG_QUALITY_REVIEW -ErrorAction SilentlyContinue
}
```

직전 실제 검증은 RAG_QUALITY_REVIEW=true를 포함한 test/bootJar 실행이며 총 41개 중 31개 통과, 10개 건너뜀, 실패/오류 0개였다. 기본 실행은 조건부 테스트의 환경 변수에 따라 통과·건너뜀 수가 달라진다. RAG_ASK_LIVE는 실제 유료 호출을 허용하는 별도 opt-in이며 이번 변경 검증에서는 활성화하지 않았다.

- 개인정보 마스킹, 질문 이력 비저장 및 본문 식별자 경고 유지
- API 예시와 적용 한계를 문서화하고 회귀·읽기 전용 검증 추가
