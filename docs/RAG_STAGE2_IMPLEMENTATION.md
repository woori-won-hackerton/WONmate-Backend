# 2단계: PDF 추출 및 조항 청킹

PDFBox 3.0.8의 `Loader`와 `PDFTextStripper`를 사용한다. Spring 애플리케이션을 시작하지 않는 개발 전용 CLI이므로 DB 접속, 엔티티 저장, 임베딩 및 OpenAI API 호출이 없다.

패키지 정리 후 `PdfExtractor`, `ArticleChunker`, `RagDebug`는 `wonit.hackathon.a1.rag`에 위치한다. `domain`에는 엔티티와 enum만 둔다. 3단계의 API·서비스·Repository·클라이언트·DTO는 각각 루트의 `controller/rag`, `service/rag`, `repository/rag`, `client/rag`, `dto/rag`로 분리했다. 전체 구조와 적재 검증 결과는 [3단계 구현 문서](RAG_STAGE3_IMPLEMENTATION.md)를 참고한다.

## 지금 구현된 기능을 예시로 보기

현재 기능은 보험 PDF를 읽어 **어느 문서의 몇 페이지에 있는 어떤 조항인지 알 수 있는 텍스트 조각**으로 만드는 것이다. 검색이나 보험 질문에 대한 답변 생성은 아직 수행하지 않는다.

예를 들어 다음 메타데이터가 있으면 해당 상품 폴더 안에서 기록된 파일명을 그대로 찾는다.

```text
documents/
└─ product_01/
   ├─ metadata.json
   └─ 통합약관_예시.pdf
```

```json
{
  "documents": [
    { "fileName": "통합약관_예시.pdf", "documentType": "TERMS" }
  ]
}
```

처리 단계와 담당 클래스는 다음과 같다.

| 단계 | 담당 | 만들어지는 정보 |
| --- | --- | --- |
| 상품 폴더·메타데이터 읽기 | `RagDebug` | 처리할 원본 PDF 경로 |
| 페이지별 텍스트 추출 | `PdfExtractor` | 실제 페이지 번호, 텍스트, 이미지 포함 여부 |
| 조항별 나누기·긴 조항 분할 | `ArticleChunker` | 조항명, 상위 주계약·특약 경로, 페이지 범위, 본문 |
| 개발용 파일 출력 | `RagDebug` | 추출 TXT, 청크 JSON, 처리 상태 보고서 |

아래는 동작을 설명하기 위한 가상 입력이다. 제1조가 실제 PDF 5쪽에서 시작해 6쪽까지 이어진다고 가정한다.

```text
[실제 PDF 5쪽]
주계약
제1조(보험금 지급)
암 진단 확정 시 보험금을 지급합니다.

[실제 PDF 6쪽]
지급 금액은 1,000만원입니다.
제2조(면책)
면책에 관한 내용입니다.
암진단특약
제1조(특약 지급)
특약에 관한 내용입니다.
```

제1조의 출력은 다음처럼 된다. `chunkIndex`는 문서마다 0부터 시작하며, 이 예시에서는 앞의 `주계약` 제목 구간이 0번이어서 제1조가 1번이다. 실제 출력 본문에는 추출된 공백·줄바꿈이 남을 수 있다.

```json
{
  "chunkIndex": 1,
  "sectionTitle": "제1조(보험금 지급)",
  "sectionPath": "주계약 > 제1조(보험금 지급)",
  "startPage": 5,
  "endPage": 6,
  "content": "제1조(보험금 지급)\n암 진단 확정 시 보험금을 지급합니다.\n\n지급 금액은 1,000만원입니다."
}
```

뒤의 특약 조항은 `암진단특약 > 제1조(특약 지급)` 경로로 구분한다. 긴 제1조를 여러 조각으로 나누더라도 각 조각에는 같은 조항명과 상위 경로를 유지하고, 각 조각에 실제로 포함된 텍스트의 페이지 범위를 기록한다.

## 실행

프로젝트 루트에서 실행한다.

```powershell
.\gradlew.bat ragDebug                          # product_01의 약관 및 요약서
.\gradlew.bat ragDebug --args="--product=product_02"
.\gradlew.bat ragDebug --args="--all"           # 전체 상품
.\gradlew.bat test --tests '*PdfPipelineTests'
```

`documents/` 바로 아래 상품 폴더를 정렬해서 순회하고 `metadata.json`의 `documents[].fileName`을 그대로 사용한다. 1단계 분류 보관용 `unmatched/`는 `SKIPPED`로 보고한다. 파일명을 추측하거나 PDF를 임의로 대신 선택하지 않는다. UTF-8과 `Path`를 사용해 한글 파일명, 공백, Windows 경로를 처리한다. 누락된 메타데이터/PDF, 잘못된 경로 및 추출 실패는 보고서에 `FAILED`로 기록하며 다른 문서는 계속 처리한다. 실패 또는 대상 없음은 명령 실패로 반환한다.

## 설정과 결과

`src/main/resources/application-local.yaml`의 `rag` 항목을 사용한다. CLI는 YAML만 읽으며 Spring 설정의 DB/API 환경변수를 해석하거나 사용하지 않는다.

- `debug.documents`: PDF 입력 폴더 (기본 `documents`)
- `debug.output`: 결과 폴더 (기본 `build/rag-debug`)
- `chunking.target-tokens`: 긴 조항 분할 목표 (750)
- `chunking.max-tokens`: 분할 상한 (1000)
- `chunking.overlap-tokens`: 동일 조항 내 중복 구간 (80)
- `chunking.chars-per-token`: 토큰 추정용 문자 비율 (1.5)

실제 모델 토크나이저를 사용하지 않는다. 기본값은 UTF-16 문자 기준 목표 1,125자, 최대 1,500자, 중복 120자다. 한국어의 토큰 수는 모델마다 다르므로 추후 실제 토크나이저로 교체할 수 있다. 짧은 조항은 합치거나 최소 길이를 강제하지 않는다. 긴 조항은 목표 길이 이후의 줄바꿈을 상한 내에서 선택하고, 긴 단일 행은 문자 경계에서 나눈다.

- `extracted/<상품>/<원본명>.txt`: 페이지 구분자를 포함한 PDFBox 추출 원문
- `chunks/<상품>/<원본명>.json`: `chunkIndex`, `sectionTitle`, `sectionPath`, `startPage`, `endPage`, `content` 배열
- `report-product_01.json` 또는 `report-all.json`: 페이지·청크 수, 빈 페이지, OCR 필요 페이지, 처리 오류 및 사용한 청킹 설정
- `review/*.png`: 로컬 샘플 테스트가 생성하는 원본 페이지 렌더링

페이지는 인쇄 번호가 아닌 **1부터 시작하는 실제 PDF 페이지**다. 원문 공백을 정리하며 페이지를 추정하지 않고, 추출 문자열의 각 위치에 원본 페이지를 연결한다. `sectionPath`에는 인식한 상위 주계약·특약명과 조항명을 담는다. 미확인 제목은 `null`이다.

## 테스트 7개가 각각 확인하는 것

테스트 코드는 `src/test/java/wonit/hackathon/a1/rag/PdfPipelineTests.java`에 있다. 아래 1~6번은 테스트가 직접 만든 PDF·문자열로 재현하는 자동 테스트이고, 7번은 로컬 실제 보험 PDF를 사용하는 테스트다. DB와 외부 API는 사용하지 않는다.

### 1. 한글 파일 경로와 실제 페이지 번호

메서드: `extractsUnicodePathAndKeepsPhysicalPagesIncludingBlankPages`

임시 경로 `한글 상품/통합 약관.pdf`에 2쪽짜리 PDF를 만든다. 1쪽은 비우고, 2쪽에는 `Printed page 99: condition A 1000 KRW`를 넣는다.

- 추출 결과는 빈 1쪽을 포함해 2페이지여야 한다.
- 2쪽의 지급 조건·금액 문자열이 추출되어야 한다.
- 생성된 청크의 `startPage`, `endPage`는 모두 **2**여야 한다. 본문에 적힌 99를 출처 페이지로 사용하면 실패한다.

이 테스트는 한글 **파일명·폴더명** 처리를 검증한다. 생성 PDF의 본문은 영문이며, 실제 한글 본문 추출은 7번 샘플에서 확인한다.

### 2. 여러 페이지에 걸친 조항, 상위 특약, 표 텍스트 보존

메서드: `preservesArticlesParentsAndTableTextWithoutInferringCells`

위의 5~6쪽 예시와 비슷한 페이지 문자열을 직접 전달한다. 표 모양의 본문도 포함한다.

```text
지급 조건    지급 금액
암 진단 확정    1,000만원
```

기대 결과는 제1조의 페이지 범위 `5~6`, 경로 `주계약 > 제 1 조 (보험금 지급)`, 특약 경로 `암진단특약 > 제1조(특약 지급)`다. 전달한 표 문자열도 그대로 본문에 있어야 한다.

이 테스트는 **추출 이후 청킹 과정이 표 문자열을 바꾸지 않는지** 확인한다. PDF의 표에서 행·열을 정확히 읽어내는지, 조건과 금액의 관계가 맞는지까지 보장하지 않는다.

### 3. 긴 조항의 분할 길이·중복·원문 누락 검사

메서드: `boundsLongArticlesAndOverlapsWithoutLosingTextOrPages`

`제1조(긴 조항)` 뒤에 `가나다라마바사 `를 600번 붙여, 실제 PDF 3쪽에 있는 긴 조항을 가정한다. 테스트 설정은 다음과 같다.

| 항목 | 테스트 값 | 문자 수 추정 |
| --- | --- | --- |
| 분할 목표 | 500토큰 | 750자 |
| 분할 상한 | 1,000토큰 | 1,500자 |
| 중복 구간 | 80토큰 | 120자 |

운영 실행 기본 목표는 750토큰이다. 테스트에서는 여러 조각이 쉽게 생기도록 목표만 500으로 낮춘다. 두 경우 모두 `chars-per-token=1.5`를 사용하는 추정치이며 실제 모델의 토큰 수를 측정하지 않는다.

검사 내용은 다음과 같다.

- 청크가 3개 이상 생성되고 각 내용이 1,500자 이하여야 한다.
- 모든 조각의 제목은 `제1조(긴 조항)`, 페이지 범위는 `3~3`이어야 한다.
- 인덱스는 `0, 1, 2, ...`로 이어져야 한다.
- 앞 청크 끝부분과 다음 청크 시작부분이 겹쳐야 한다. 가장자리 공백 제거를 고려해 이 입력에서는 110자 이상의 중복을 확인한다.
- 중복 부분을 한 번만 남기고 모든 청크를 이어 붙이면 `원문.strip()`과 같아야 한다.

마지막 검사는 단순히 길이만 맞추는 것이 아니라 **분할하면서 원문 일부가 사라지거나 추가되는 문제**도 잡기 위한 것이다.

### 4. 진행을 막을 수 있는 잘못된 설정 거부

메서드: `rejectsSettingsThatPreventProgress`

`목표=500`, `상한=1000`, `중복=500` 설정을 만든다. 중복이 목표만큼 크면 다음 분할 구간이 제대로 전진하지 못할 수 있으므로, 설정 생성 시 `IllegalArgumentException`이 발생해야 한다. 이 테스트는 이 조합 하나를 검사하며 설정 검증의 모든 분기를 검사하는 것은 아니다.

### 5. 이미지 전용 페이지의 OCR 필요 여부

메서드: `identifiesImageOnlyScannedPagesAsRequiringOcr`

글자가 없는 작은 이미지만 들어 있는 `스캔.pdf`를 만든다.

| 입력 페이지 | 기대 `needsOcr()` |
| --- | --- |
| 텍스트 없음 + 이미지 있음 | `true` |
| 텍스트 없음 + 이미지 없음 | `false` |

현재 구현은 이미지 전용 페이지를 구분한다. OCR로 글자를 인식하지는 않으며, 이 테스트가 CLI 보고서의 모든 상태 분기까지 검증하는 것은 아니다.

### 6. 조항 제목과 본문 인용·목차 구분

메서드: `recognizesBracketedHeadingsButNotCrossReferencesOrTableOfContents`

아래 행을 한 페이지에 넣고 새 조항으로 인식하는지 확인한다.

| 입력 행 | 기대 처리 |
| --- | --- |
| `제1조 【목적】` | 새 조항 시작 |
| `제 3 조(의료기관)의 규정에 따른 병원` | 본문 인용이므로 기존 조항 내용에 유지 |
| `제2조 【정의】 .... 30` | 점선·페이지가 있는 목차이므로 기존 내용에 유지 |
| `제2조 【용어】` | 새 조항 시작 |

최종 청크는 주계약 제목 구간 1개와 조항 2개로 총 3개다. 목차 텍스트를 삭제하는 기능은 없으며, 새 조항의 경계로 사용하지 않는다는 의미다.

### 7. 실제 약관·요약서와 원본 대조용 이미지 생성

메서드: `validatesRealSampleArtifactsAndRendersPagesForTableReview`

`documents/product_01/`의 PDF를 직접 읽어 추출·청킹을 다시 수행한다. 이전에 저장한 청크 JSON을 읽어 검사하는 방식은 아니다. 해당 폴더가 없으면 이 테스트만 건너뛴다.

| 대상 | 자동 검사 내용 |
| --- | --- |
| 모든 청크 | 비어 있지 않은 청크 목록, 유효한 페이지 범위, 내용 길이 1,500자 이하 |
| 통합약관 | 총 320쪽, 실제 27쪽의 `주계약 > 제1조 【목적】` 존재 |
| 통합약관 특약 | 실제 104쪽의 `무배당동양연금전환특약 > 제1조 【목적】` 존재 |
| 상품요약서 | 총 14쪽, 실제 2쪽에 `표준형 해약환급금의 50%`와 `95%` 문자열 존재 |

추가로 다음 PNG를 `build/rag-debug/review/`에 만든다.

- `terms-27.png`: 주계약 첫 조항. 인쇄 번호는 25지만 실제 PDF 페이지는 27이다.
- `terms-104.png`: 특약 첫 조항. 인쇄 번호는 102지만 실제 PDF 페이지는 104다.
- `terms-319.png`: 신체부위 설명도 이미지.
- `summary-2.png`: 환급률 표가 있는 상품요약서 페이지.

PNG 생성은 자동으로 실행하지만 **PNG의 내용이 맞는지 판정하는 과정은 사람의 육안 검토**다. 예를 들어 `summary-2.png`와 추출 TXT의 `PDF PAGE 2`를 나란히 보고, 원본 표의 조건과 50%·95%·100% 금액이 어떤 순서로 추출됐는지 확인한다.

## 자동 테스트와 전체 실행 검증의 차이

`test --tests '*PdfPipelineTests'`는 위 7개 테스트를 실행한다. `ragDebug --args="--all"`은 전체 PDF를 처리하는 개발 명령이며 JUnit 테스트가 아니다.

이 단계에서는 전체 명령 실행 후 출력 JSON을 별도로 검사해 인덱스 순서, 페이지 범위, 빈 내용 여부, 길이 상한을 집계했다. 그 결과가 `build/rag-debug/verification.json`이다. 이 집계 파일은 `ragDebug`나 JUnit이 자동 생성하는 파일이 아니며, 재실행 시 보고서 `report-all.json`과 각 청크 JSON은 갱신되지만 이 집계는 별도 검증이 필요하다.

검증 범위를 구분하면 다음과 같다.

| 구분 | 확인한 범위 |
| --- | --- |
| 재현 가능한 자동 테스트 | 생성 PDF·문자열의 추출/청킹 동작과 실제 상품 1의 대표 값 |
| 전체 출력 구조 검사 | 20개 PDF에서 생성된 모든 청크의 인덱스·페이지·내용·길이 |
| 원본 이미지와 육안 대조 | 상품 1의 대표 조항·특약·환급률 표·이미지 설명도 |
| 아직 보장하지 않는 부분 | 전체 문서 모든 표의 의미 관계, 모든 제목/특약 계층의 정확성, OCR 결과, 실제 모델 토큰 수 |

## 검증 결과 및 한계

`PdfPipelineTests`는 PDF 생성 기반 추출, 한글 경로, 빈 페이지, 이미지 전용 스캔 감지, 페이지 보존, 조항·상위 특약 인식, 본문 조항 참조/점선 목차 제외, 긴 조항 상한·중복·원문 복원 및 표 텍스트 보존을 검사한다. 로컬 상품 PDF가 있으면 실제 상품 1의 2개 문서도 검증하며, 없으면 해당 로컬 검증만 건너뛴다.

샘플 검증에서 통합약관 320페이지와 상품요약서 14페이지를 추출했다. 실제 PDF 27페이지(인쇄 25페이지)의 주계약 `제1조 【목적】`, 실제 PDF 104페이지(인쇄 102페이지)의 `무배당동양연금전환특약 > 제1조 【목적】`를 렌더링과 대조했다.

최종 전체 실행은 10개 상품, PDF 20개, 13,934페이지에서 19,306개 청크를 생성했다. 모든 출력 JSON의 순차 인덱스·페이지 범위·빈 내용·길이를 확인했으며 위반은 없었다(최장 1,495자). 문서 12개는 `EXTRACTED`, 8개는 `PARTIAL_OCR_REQUIRED`이며 `unmatched/`는 `SKIPPED`다. 원본 대조는 위 샘플에 대해 수행했으며 전체 문서의 모든 표를 육안 검증한 것은 아니다. 새 테스트 7개와 기존 매핑 테스트 1개가 통과했다. 상세 집계는 `build/rag-debug/verification.json`, 실행 로그는 `build/rag-debug/validation.log`에 있다.

상품요약서 PDF 2페이지의 환급률 표에서 50%·95%·100% 텍스트는 추출되지만 여러 줄인 조건과 금액이 PDFBox 출력에서 교차한다. **표의 행·열 관계는 보장하지 않으며 내용을 재구성하지 않는다.** 모든 문서는 보고서의 `tableExtractionStatus=UNVERIFIED_TEXT_ONLY`를 유지한다. 지급 조건과 금액은 원본 표와 대조해야 한다.

통합약관의 텍스트 없는 페이지는 2·319·320페이지다. 319페이지는 렌더링으로 신체부위 설명도 이미지임을 확인했다. 텍스트 없이 이미지가 있는 페이지는 `ocrRequiredPages`에 기록하고 문서를 `PARTIAL_OCR_REQUIRED`로 보고한다. 전체 페이지가 비어 있으면 `OCR_REQUIRED`, 기타 빈 페이지가 있으면 `REVIEW_REQUIRED`다. OCR 자체는 수행하지 않는다. 일부 텍스트와 스캔 이미지가 섞인 페이지 및 이미지 내부의 표는 이 방식으로 완전히 탐지할 수 없다.

조항·특약 제목 인식은 독립 행을 대상으로 하는 휴리스틱이다. 괄호 `()`, `（）`, `【】`, `[]`와 조항 번호의 공백을 허용한다. 줄바꿈된 제목이나 안내문 안의 조항 인용, 특약 제목이 없는 구간, 별표·법령 부록의 계층은 추가 조정이 필요할 수 있다. 텍스트는 보존하며 제목·경로를 법적 구조의 확정값으로 사용하지 않는다.
